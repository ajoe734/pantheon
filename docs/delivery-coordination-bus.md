# Delivery Coordination Bus

Last updated: 2026-04-14
Status: implementation guide for the Pantheon cross-repo delivery bus
Tier: L2 Planning & Execution
Scope: multi-repo coordination files, GitHub issue flow, worker routing, and Lovable trigger policy
Conflict rule: this guide explains the delivery bus; it does not override Pantheon runtime or BFF policy

## 1. Purpose

Pantheon now supports a delivery bus that treats GitHub as the cross-repo coordination surface while keeping Pantheon itself as the runtime and governance authority.

This bus is for:

- feature handoffs between Pantheon and `front-ai-trading-system`
- structured BFF gap reporting
- contract-ready notifications
- human-triggered Lovable UI tasks
- runtime / engine escalation when Pantheon cannot resolve the change alone

This bus is **not** the runtime control plane for kill-switch, rollback, or operator execution authority.

## 2. Core Roles

- `Pantheon`: owns BFF contracts, command shaping, auth/RBAC, lifecycle, governance
- `front-ai-trading-system` (`ajoe734/front-ai-trading-system`): owns pages, components, UX, state rendering, and BFF client wiring
- `GitHub`: owns delivery coordination history, issues, comments, PRs, labels, and audit trail
- `Resident Orchestrator`: watches `ai-status.json`, `.coordination/*.yaml`, and GitHub comments; dispatches workers and writes back delivery state
- `Lovable`: UI accelerator only; it is explicitly human-triggered and must not be treated as a headless execution engine

## 3. Coordination Files

Pantheon scans local repo checkouts for:

- `.coordination/requests/*.yaml`
- `.coordination/responses/*.yaml`

Supported payloads:

- `bff-gap`: UI lane requests Pantheon BFF changes
- `ui-done`: UI lane signals that Lovable/front-end implementation is ready for Pantheon review/integration follow-up
- `frontend-feedback`: UI lane publishes the required feedback bundle and changed-file summary for Pantheon review
- `contract-ready`: Pantheon signals front-end readiness
- `lovable-ui-task`: generated by Pantheon after `contract-ready`
- `backend-delivery`: Pantheon publishes the next backend or contract delivery note for the front repo
- Pantheon mirrors `contract-ready`, `lovable-ui-task`, prompt packets, request templates, and referenced BFF docs/examples into the front-end checkout so the Lovable-connected repo sees the same handoff packet
- `needs-runtime`: Pantheon needs runtime-platform help
- `needs-engine`: runtime lane needs LEAN capability work
- `dispatch-request`: manual replay / dispatch trigger from GitHub comment commands

## 4. Worker Routing

Default worker mapping:

- `pantheon-bff-worker` -> `Codex`
- `front-sync-worker` -> `Codex`
- `front-ui-worker` -> `Copilot`
- `runtime-worker` -> `Gemini`
- `engine-worker` -> `Claude` with explicit human approval
- `qa-worker` -> `Claude`

## 5. GitHub Commands

Coordination issues accept:

- `/dispatch pantheon-bff F-xxx`
- `/dispatch front-ui F-xxx`
- `/needs-runtime F-xxx`
- `/contract-ready F-xxx`
- `/approve-engine F-xxx`

These commands do not bypass Pantheon authority. They only queue the next worker or replay an existing handoff.

## 6. Lovable Lane

Pantheon does **not** treat Lovable as a zero-touch worker.

The current supported flow is:

1. Pantheon writes `contract-ready`
2. Orchestrator generates `lovable-ui-task` and a short prompt packet
3. A human opens the Lovable project and explicitly submits the task
4. The front repo writes the required feedback bundle and `.coordination/requests/F-xxx-frontend-feedback.yaml`
5. If the screen is complete, the front repo also writes `.coordination/requests/F-xxx-ui-done.yaml`; if blocked on contract truth, it writes `.coordination/requests/F-xxx-bff-gap.yaml`
6. Pantheon supervisor sees the request payloads and dispatches the next review or integration worker automatically
7. Pantheon writes `.coordination/responses/F-xxx-backend-delivery.yaml` when contract or BFF follow-up is ready for the next UI cycle

This design keeps Lovable high leverage without making the entire pipeline depend on an undocumented headless project-execution API.

## 7. Replay Discipline

- `repository_dispatch` is the target transport for normal cross-repo machine triggers.
- `workflow_dispatch` is the replay path for a stalled or failed step.
- Replay must point at an existing payload path and commit ref; it is a transport retry, not a payload-edit workflow.
- If a payload needs different contents, Pantheon or the front repo must publish a new payload and run a normal loop step instead of replaying the old one.
