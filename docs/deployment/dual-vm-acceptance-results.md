# Dual-VM Acceptance Results

Acceptance record for `DEPLOY-009`.

This artifact is paired with [`scripts/smoke_test_dual_vm.sh`](/home/edna/code/pantheon/scripts/smoke_test_dual_vm.sh:1) and captures what that smoke proves, what must be recorded after a real VM run, and the current boundary of the execution-plane paper runtime package.

## Scope

The dual-VM acceptance bar for this repo baseline is:

1. VM-1 creates and dispatches a `DeploymentPlan`
2. VM-2 `runtime-manager` creates the authoritative `RuntimeBinding`
3. VM-1 deployment saga records `binding_created` and `runtime_active`
4. VM-1 telemetry ingest accepts events whose binding identity is resolved from VM-2
5. VM-1 can trigger kill-switch and rollback actions that VM-2 executes

This repo now ships a dedicated VM-2 paper execution runtime package on top of
the original DEPLOY-008 split. The `pantheon-paper-runtime` container proves:

- paper-runtime process health
- a concrete signal-consumer/runtime service surface, not only import checks
- Pantheon ↔ LEAN bridge availability for downstream packaging
- adjacency to `runtime-manager`, broker adapter, and exchange adapter

It still does **not** by itself prove the first integrated governed paper
execution packet; that remains `OSS-004C`.

## Preconditions

Before recording a passing run:

- VM-1 control stack is healthy from `docker-compose.control.yml`
- VM-1 deployment service is started separately, for example:

```bash
uvicorn services.deployment.service:app --host 0.0.0.0 --port 8006
```

- VM-1 telemetry has remote runtime-manager lookup configured:

```bash
export PANTHEON_RUNTIME_MANAGER_URL="http://<vm2-ip>:28081"
export PANTHEON_RUNTIME_MANAGER_TOKEN="runtime-control-internal"
```

- VM-2 execution stack is healthy from `docker-compose.exec.yml`
- VM-2 published ports for `runtime-manager`, `pantheon-paper-runtime`, and optionally the mock broker/exchange sidecars are reachable from the acceptance runner

## Canonical Command

Run from VM-1 or a bastion host that can reach both VMs:

```bash
bash scripts/smoke_test_dual_vm.sh \
  --control-deployment-url http://<vm1-ip>:8006 \
  --control-telemetry-url http://<vm1-ip>:38083 \
  --exec-runtime-manager-url http://<vm2-ip>:28081 \
  --exec-paper-runtime-url http://<vm2-ip>:28110 \
  --exec-broker-url http://<vm2-ip>:28097 \
  --exec-exchange-url http://<vm2-ip>:28098 \
  --runtime-manager-token runtime-control-internal \
  --output-dir /tmp/pantheon/dual-vm-acceptance-$(date -u +%Y%m%dT%H%M%SZ)
```

The script emits JSON request/response artifacts plus a `summary.json` file that should be attached to the acceptance record.

## Acceptance Mapping

| Acceptance item | Proven by |
|---|---|
| `DeploymentPlan -> RuntimeBinding` crosses VM boundary | `plan-dispatch-response.json` + `runtime-deploy-response.json` |
| paper runtime starts on VM-2 | `vm2_paper-runtime.json` health output |
| telemetry events return to VM-1 | telemetry ingest responses + stats increment |
| VM-1 kill-switch stops the VM-2 binding | `kill-switch-response.json` shows `binding_action.binding.status=paused` |
| VM-1 rollback executes on VM-2 | `rollback-response.json` shows `old_binding.status=retired` and `new_binding.status=active` |

## Current Limitation

The smoke intentionally stops short of claiming:

- a real LEAN order execution loop
- broker-side order acknowledgement
- end-to-end signal delivery from production `SignalStore`

Those require a governed end-to-end paper execution run that includes real
signal injection and archived evidence. `DEPLOY-009` therefore remains a
**cross-plane acceptance harness**, while `OSS-004C` owns the first integrated
EP4 proof packet.
