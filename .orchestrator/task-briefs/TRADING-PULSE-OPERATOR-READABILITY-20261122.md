## A 與 B 共用資料契約

沿用 `GET /bff/management/trading-pulse` 與其 `/rankings` 端點、既有 envelope、列鍵、指標及排名區塊。以下 additive 欄位是並行工作起點。A 和 B 同步記錄必要的實際欄位對照於兩邊 contract tests，D 僅消費 B 的型別。

| 位置 | 共同語義 |
|---|---|
| `summary.operator_scope` | `status` 表達名單已核實、部分或不可用。`persona_count`、`runtime_count` 分別計算，`by_stage` 保留現行階段與對應人數。無法確認的數量為 null。 |
| `summary.pnl_groups[]` | 各組 `stage`、`currency`、`period_start_at`、`period_end_at` 或明確可比的期間標識、`as_of`、`value`、`covered_persona_count`、`eligible_persona_count`。先核對損益定義、幣別與期間。缺少來源或無法證實可比時，留在個別列並說明。 |
| 現有執行列 | 保留原本 ID。附 `persona_name`、`strategy_name`、`underlying_symbol` 及可核實的範圍。沿用來源的實際階段、交易模式和執行狀態，包括有資料的 canary。 |
| `row.performance_context` | 保留來源已有的 `ledger_fill_count`、`pnl_currency`、`pnl_period_start_at`、`pnl_at`、`fill_rate_details`（原分子、分母、單位）與來源證實的最後成交時間。按指標提供 `metric_reasons`。當下的連線/快照時間與業務時間各自保留。 |
| `row.latest_outcome` | 依目前綁定與範圍取得有根據的最近交易結果，含 `occurred_at`、`reason_code`、`submitted_to_broker`、`requested_quantity`、`required`、`available`、`currency`、`journey_id` 及可用的既有焦點鍵。缺少來源的值可為 null。 |
| 各排行 item | 保留相同人名、標的、指標單位，以及現有 `links` 或實際可解析的導航鍵。排行母體與總覽一致。只有能排序的已知值可入列，顯示指標適用範圍。 |

當名冊與交易證據齊全時，首頁依序呈現模擬/實盤的營運人數、可比的已知損益與涵蓋人數、值得留意的交易、具名 Persona 明細，再呈現有可比資料的排行。狀態文字要能分辨「尚未成交」、「尚未有委託」、「資料暫時無法取得」與「上次資料已過期」。晚到的資料可以更新當期狀態，歷史事件使用發生當時的綁定。模擬沒有適用的實盤基準時摘要一次即可。技術診斷預設收合，進入交易旅程的操作要在桌面和手機上直接可見。

## 任務與驗收條件

### A　交易脈動與排行共用營運名單、帳本事實及拒單原因

`BFF-TRADING-PULSE-OPERATOR-FACTS-20261122`　Codex2 實作，Antigravity2 覆核。

RC6 WP6.1/6.2/6.3。負責總覽與排行兩個讀取端點及功能唯讀驗收程式。沿用既有 Persona、策略、綁定、帳本、遙測、交易旅程與資料可用性介面。依共同規格填入新增欄位，維持既有呼叫端契約。

1. 在兩個端點的共同入口依目前租戶、有效綁定和 Persona 身分決定營運名單。重用 is_probe_or_test_persona 與現有名冊，不按固定 ID、名稱或有無成交硬編碼。所有清單、摘要、分母、覆蓋、排行、診斷 ID 和基準比較使用同一名單。區分 Persona 數與執行個體數。名冊讀取失敗須揭露範圍無法確認，避免宣告零人或洩漏未核實身分。批次沿用已有索引，避免為每列掃描整份帳本或交易旅程。
2. 核對同租戶、環境、綁定與時間範圍。正確配對的帳本有 0 成交時給 0 筆；遙測 no_fills 且無損益樣本時保留空值及原因。從 fill_rate_details 保留成交量、意向量與單位，有意向量才計算比率，0/452 為 0%，0/0 為尚無可計算的成交率。保留真零滑價、損益、回撤，區分資料過期、來源無法讀取與沒有交易。用既有事件或交易旅程關聯證明拒單原因、數量、所需/可用金額、是否送出以及時間。無法證實的欄位留空。禁止將同名舊綁定的成交或原因接到現在的綁定。
3. 摘要附上模擬與實盤分組、不同人數、每組損益的幣別、期間、取樣時間和涵蓋人數；只加總相同幣別、可比期間與交易模式。逐項指標的分母清楚呈現。保留來源使用的成交率算法並命名；區分最新回報、最後成交與快照。僅實際需要的基準做比較。排行使用合格、可比較、有觀測值的列，傳遞人名、標的、單位、原因和可導航目標。夏普樣本不足、變異為零和未知沿用各自來源狀態。測試同一 Persona 多綁定、跨租戶、空名單、部分資料與來源故障、混合幣別/環境、舊綁定及舊消費端。
4. 交付可單獨執行的唯讀 API probe 與有正反例的離線測試。用受驗租戶獨立的名冊、帳本或既有證據核對總覽與排行，故意混入探針、錯誤分母、將零改空、將未知改零、移除拒單依據時應失敗。比對同一時間範圍；失去來源時回報不可驗證。保留管理駕駛艙及其他既有消費端的相容性。來源任務以 dev 合併與測試交接給 E。
