## 1. What AG-DES-CARD-001 Delivers

AG-DES-CARD-001 defines the typed **WorkshopCard projection contract** for the Agora Strategy Workshop frontend. Cards are BFF projections bound from structured backend data; the frontend must not parse arbitrary LLM markdown to derive card type or card meaning.

### 1.1 Primary deliverables

| Deliverable | Canonical target path | Source document |
|---|---|---|
| WorkshopCard JSON Schema | `services/control-plane/specs/agora/v4/workshop_card.schema.json` | `design-closure-round2/schemas/workshop_card.schema.json` |
| Card prose contract (12 card types, field definitions) | `docs/04/pantheon_agora_cross_repo_2026-06-20/design-closure-round2/05_workshop_card_contracts.md` | same file |
| Card list route in v1.3 OpenAPI | `services/control-plane/openapi/agora_v1_3.openapi.yaml` | `design-closure-round2/08_openapi_v1_3_delta.yaml` §E |
| v1.3 bundle index reference | `services/control-plane/specs/agora/bundle_index.v1_3.json` | via `AG-XR-OPENAPI-004` |

### 1.2 Card types defined

The schema (`workshop_card.schema.json`) enumerates exactly 12 card types:

```
user_strategy_description
servant_reconstruction
completeness_update
missing_definition
next_question
research_plan_proposal
research_progress
research_result
consult_result
version_patch_proposal
version_compare
readiness_gate
```

Each card has a common typed envelope (§E1 of the card contracts) plus a card-type-specific payload documented in §E2–E13.

### 1.3 Card list BFF route

```
GET /bff/agora/workshops/{workshop_id}/cards
```

Response schema: `ListEnvelope` wrapping `WorkshopCard` objects. The workshop detail response may also embed `cards[]` inline. The SSE stream carries card-update references; it does not resend every large card payload.

## 5. Reviewer Attention Points

1. **Schema payload extensibility:** The schema accepts `additionalProperties: true` on `payload`. This is intentional — BFF validates payload shape per card type at the application layer. Reviewer should confirm this matches the parent's planned BFF validation strategy.

2. **Twelve card types are exhaustive for v1.3:** Any new card type requires a v1.4 additive contract, not an ad-hoc extension. Reviewer should confirm that the 12 types cover all UI affordances expected by `AG-FE-SW-001` and `AG-FE-SW-002`.

3. **`servant_reconstruction` distinguishes trader-stated vs servant-inferred:** The `causal_chain[]` carries confidence and `evidence_refs[]`; `servant_inferences[]` carries `needs_confirmation`. The frontend must not flatten these into a single list. Confirm this is surfaceable in the UI design.

4. **`research_result` labels real/fixture/stub:** The card must visibly label the backend mode. Reviewer should confirm whether the label is in `payload.backend_mode` or a top-level card envelope field. The current schema puts it in `payload`.

5. **Card staleness:** The `stale` status is defined but the stale trigger is not specified in the card contract (it is managed at the SSE + completeness-update layer). Reviewer should confirm the parent is aware of this and does not expect a stale-trigger rule within `AG-DES-CARD-001`'s scope.

6. **No `AG-XR-OPENAPI-004` dependency on this packet:** This acceptance packet is a support artifact and does not gate `AG-XR-OPENAPI-004`. That task's definition of done is set in the Round 2 master response and the dispatch unblock matrix. However, the parent reviewer of `AG-DES-CARD-001` should verify that `AG-XR-OPENAPI-004` includes `workshop_card.schema.json` in its scope list.
